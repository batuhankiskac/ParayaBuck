# Capital-fragmentation audit

Scope: configuration-derived sizing and broker mechanics only. No NAV history, fills, fee outcomes, or performance data were used.

## Meaningful-size controls in code

The execution policy suppresses weight drift below 0.005 of account equity and planned order notional below $10 (`config/settings.yaml:227-228`; `src/parayabuck/execution/portfolio.py:62-82,493-529`). The planner also floors quantity to broker asset increments and requires broker minimum quantity and notional. The submission gateway repeats these checks after flooring (`src/parayabuck/execution/portfolio.py:514-530`; `src/parayabuck/execution/alpaca_orders.py:165-204`). Alpaca asset metadata supplies minimum size, trade increment, and minimum notional, with repository fallbacks if metadata is absent (`src/parayabuck/execution/alpaca.py:524-544`). The code does not inspect an explicit `fractionable` flag in this path; broker acceptance remains authoritative.

These are **minimum order-delta** controls, not a minimum target-position weight or minimum post-trade holding size. `PositionSnapshot.is_flat` requires exactly zero quantity, so any tiny nonzero fractional/residual broker holding consumes a full account slot (`src/parayabuck/core/models.py:188-199`; `src/parayabuck/execution/portfolio.py:276-306`). An order below threshold may be skipped while a tiny position remains. No repository policy establishes that a position must represent a specified fraction of equity to justify one slot.

At current static limits, two crypto names share 5% at 2.5% each under the equal-weight crypto strategy (`config/settings.yaml:165-173`; `src/parayabuck/portfolio/crypto_low_variance_hysteresis.py:59-92`). Four equity slots can express at most 40% under the 10% per-name cap, even though the equity sleeve permits 55%. To express 55% across six equity names would require 9.17% *if* equal weighted; V3 actually uses inverse-volatility sizing, so equal weight is illustration only (`config/settings.yaml:148-157`; `src/parayabuck/portfolio/equity_residual_momentum_v3.py:1-25`; `src/parayabuck/execution/portfolio.py:242-249`). The unused 15 percentage points in the two-crypto/six-total geometry remain cash or other non-equity capacity; no assumption about expected returns follows.

At a hypothetical higher cap, per-name weight can become smaller, but higher cap does not itself force smaller positions: sleeve and per-name rules remain. A possible failure mode is an inverse-vol target or scaled residual order falling below the $10/broker minimum or 0.5% rebalance band, so intended weights do not translate into orders. Without a specified account equity and broker asset increments, one cannot derive an economically meaningful maximum count from those thresholds. The repository has no per-position minimum weight, fee-to-notional budget, or slippage-to-notional policy that independently selects six.

Capital-fragmentation concern is therefore real as an implementation consideration, but **the exact six cap is not derived from an explicit minimum-size policy**. A future architecture study would need a prospective account-size envelope and deterministic order-feasibility gate, without consulting prior realized holdings or performance.
