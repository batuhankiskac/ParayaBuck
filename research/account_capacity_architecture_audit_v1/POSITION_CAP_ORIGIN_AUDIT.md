# Origin of the six-position setting

**Classification: `ORIGIN_UNRESOLVED`.** The repository proves when the value and its account-wide implementation appeared. It does not give a risk budget, broker rule, operational capacity calculation, or strategy derivation selecting the number six. A later implementation comment calls the limit an account-level cap; that states semantics, not the reason for six.

This audit uses configuration, source, commit metadata, and diffs only. No historical holdings, candidate outcomes, or strategy economics were inspected.

Current [`config/settings.yaml`](../../config/settings.yaml) lines 175–184 explicitly set `risk.max_positions: 6`. [`src/parayabuck/config.py`](../../src/parayabuck/config.py) lines 209–239 still define the generic `RiskLimits.max_positions` fallback as **5**, while [`src/parayabuck/execution/portfolio.py`](../../src/parayabuck/execution/portfolio.py) lines 86–124 define a `PortfolioRiskLimits` fallback of **6** and map the loaded config value into the runtime overlay. Thus the active configured setting is six; a programmatic or omitted-config use of defaults could differ. This is a configuration-default inconsistency to note, not evidence that six was chosen by a risk proof.

**Motive test.** The tracked lineage supports “inherited, revised internal policy” as a description of the setting. It does not prove `EXPLICIT_RISK_DESIGN`, `EXPLICIT_OPERATIONAL_CONSTRAINT`, `BROKER_OR_API_CONSTRAINT`, or `STRATEGY_SPECIFIC_DESIGN`. It would overstate the evidence to classify the 2026 six as deliberately calibrated or arbitrary. The requested single origin label is therefore `ORIGIN_UNRESOLVED`.

**Present role evidenced in source.** The overlay applies a hard cardinality limit before sleeve/gross scaling, retaining ranked targets where ranks exist and emitting `position_count_limit` when trimmed ([`src/parayabuck/execution/portfolio.py`](../../src/parayabuck/execution/portfolio.py), lines 265–345). That can bound the number of distinct holdings and associated orders. It does not independently cap dollars, notional, liquidity, or total exposure; those have separate controls documented in `EXISTING_RISK_CONTROLS.md`. The existence of that distinct cardinality function does not establish that **six** is the correct threshold.
