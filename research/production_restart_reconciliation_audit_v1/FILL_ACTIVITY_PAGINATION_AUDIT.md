# FILL activity enumeration

Classification: **FILL_ACTIVITY_PAGINATION_INCOMPLETE_CONFIRMED** under an incomplete/invalid page response. A normal conforming Alpaca response is paged exhaustively; this is a failure-policy defect, not the old unconditional first-page bug.

\`ReconciliationService._reconcile_fill_activity_fees\` (\`src/parayabuck/execution/alpaca_reconciliation.py:122-283\`) calls the Alpaca Trading API \`GET /v2/account/activities/FILL\` through the SDK-relative \`/account/activities/FILL\`, with \`direction=desc\`, \`page_size=100\`, optional \`after=watermark-24h\`, and the last activity's ID as \`page_token\`. The Trading API default/max size is 100; the token is the last activity ID, and descending pages precede it: [Trading API activities](https://docs.alpaca.markets/us/reference/getaccountactivities-2), [activity object and pagination](https://docs.alpaca.markets/us/docs/account-activities). FILL includes partial and full fills; the activity has \`qty\`, \`cum_qty\`, \`leaves_qty\`, \`type\`, order ID, and transaction time. The queried type excludes non-FILL activity/correction channels; [Alpaca's activity event guide](https://docs.alpaca.markets/us/docs/activity-sse) documents trade corrections/busts on its newer activity stream. This audit did not prove that any correction affected this repository.

Normal pagination advances through full pages and stops on a short page. However, a repeated full page or missing next ID logs a warning and **breaks as success**, then advances the watermark from the pages already seen. A non-list payload is converted to \`[]\` and also returns success. The offline characterization tests reproduce both paths. A thrown later-page exception returns \`False\` and does not process partial pages, which is safer.

Materiality is bounded by actual consumers. Activities update fee records, recover ledger BUY fills by broker order ID, and recover SELL execution/realized-P&L events; \`fill_activities_reconciled=False\` guards stale equity-ledger closure (\`alpaca_reconciliation.py:365-380\`). A false success can skip those recoveries and permit the stale close path. It does **not** directly create a second portfolio order: portfolio order IDs are separately persisted and broker-checked. Broker positions and OPEN orders remain separately fetched. A skipped fee can leave fee/P&L telemetry inaccurate; a missed fill can produce ownership drift and halt rather than duplicate exposure.
