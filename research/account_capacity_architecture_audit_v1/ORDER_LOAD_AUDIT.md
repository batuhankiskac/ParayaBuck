# Order-load audit

Scope: static order-path and request-count structure; no order history, throughput measurements, or economic outcomes.

## Decision and submission path

The equity product decides weekly, crypto every 96 hours (`config/settings.yaml:140-173`). The strategy targets at most eight equity and two crypto names; the account overlay trims positive targets to six combined and applies sleeve/gross limits (`src/parayabuck/execution/portfolio.py:263-377`). The planner produces at most one net delta per approved `(market, symbol)` in a decision, sorts sells before buys, and suppresses tiny drift, below-minimum quantities/notional, and symbols with working orders (`src/parayabuck/execution/portfolio.py:425-554`). This is not an order-rate guarantee: a rebalance can involve both exits and entries.

For a simple complete replacement of `C` managed held names by `C` new names, static target-order envelope is `C` SELLs plus `C` BUYs: 12 at C=6, 16 at C=8, 20 at C=10. These are illustrative *portfolio rebalance* counts, not exact broker API calls or worst-case counts across retries, protection orders, cancellations, manual activity, or multiple decision times. With the current strategies, a decision's new positive targets cannot exceed eight equity plus two crypto before account trimming. Partial quantity changes can create orders for kept names as well as exits/entries; quote or asset-metadata requests are additional API work.

The runtime persists a two-phase execution when sells and buys coexist: submit sells, wait for terminal status, refresh account, re-run the overlay/planner, size buys to cash/gross/LIVE dollar capacity, then submit buys (`src/parayabuck/portfolio/runtime_service.py:1130-1208,1210-1300,1339-1469,1520-1593`). A failed or partial sell does not release its capacity by assumption. Each `_submit_orders` iteration checks persisted idempotency state and writes a `submitting` row before calling the broker (`src/parayabuck/portfolio/runtime_service.py:1594-1665`). Alpaca adapter checks broker asset rules and for an existing same-symbol open order before submitting a market order; equity uses DAY and crypto GTC (`src/parayabuck/execution/alpaca_orders.py:165-225`). This increases per-order REST work relative to the simple SELL+BUY count.

The engine orders simultaneous markets crypto first and passes actual planned BUY slots to equity; a shared lock and account snapshot lease constrain overlapping decisions (`src/parayabuck/runtime.py:3073-3097,3102-3120,3213-3244,3518`). Startup and restart use the same ordering (`src/parayabuck/runtime.py:2482-2508,3537-3567`). Broker-wide open-order discovery is used for suppression (`src/parayabuck/execution/alpaca.py:546-557`), while account-local persisted nonterminal rows protect against lagging broker visibility (`src/parayabuck/portfolio/runtime_service.py:1473-1517`). Trade updates and restart recovery add reconciliation work rather than blindly resubmitting (`src/parayabuck/portfolio/runtime_service.py:1210-1336`).

## Architectural reading

More count capacity can increase per-rebalance requests and outstanding order states, but the code contains no demonstrated API throughput threshold at six. The six-position limit is not a substitute for the separate order idempotency, open-order, freshness, two-phase, and cash/buying-power checks. A migration study would need a frozen operational load budget and broker-rate evidence; this audit did not measure production load. Tests demonstrate cross-market reservation and restart behavior (`tests/test_multi_market_portfolio.py:410-555`; `tests/test_paper_reliability_restart.py:276-318`), but do not establish a throughput ceiling for 8 or 10 names.
