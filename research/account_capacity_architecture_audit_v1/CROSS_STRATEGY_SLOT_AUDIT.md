# Cross-strategy slot audit

Scope: current account architecture, no historical portfolio outcomes.

## Shared resources and non-equivalent slots

Equity and crypto run as separate `PortfolioRuntime` instances but use the same account broker, shared portfolio repository, six-slot `PortfolioRiskLimits`, 0.60 gross ceiling, and 0.40 cash buffer (`src/parayabuck/runtime.py:945-991`; `src/parayabuck/execution/portfolio.py:112-125,263-377`). The risk overlay counts `(market, canonical_symbol)` across both markets, plus pending and external claims. The engine explicitly runs crypto before equity for simultaneous decisions and reserves actual planned crypto BUY slots (`src/parayabuck/runtime.py:3073-3097,3111-3120,3518,3537-3567`). This is a production slot-allocation rule, not an incidental traversal order.

Two crypto names at the current 5% sleeve are ordinarily 2.5% targets each under the equal-weight strategy (`config/settings.yaml:165-173`; `src/parayabuck/portfolio/crypto_low_variance_hysteresis.py:59-92`). Two equity names may each reach 10%. The count cap charges each name one slot despite different target notional and execution mechanics (crypto GTC versus equity DAY in `src/parayabuck/execution/alpaca_orders.py:205-211`). Gross, sleeve, and per-asset limits already distinguish exposure size; count measures number of distinct broker positions/order claims and operational objects. It is therefore meaningful as a shared operational complexity ceiling, but not a risk-equivalent unit across assets.

With two crypto slots active and the six-total cap, equity has at most four slots and 40% target capacity under the 10% equity single-name rule. A single active crypto slot leaves five equity slots and 50% capacity. Zero leaves six equity slots and up to 55% under the equity sleeve, subject to strategy sizing and other risk limits (`src/parayabuck/execution/portfolio.py:263-377`; `tests/test_multi_market_portfolio.py:225-269,410-555`). This is a structural cross-strategy interaction: crypto occupancy changes equity selection and attainable target exposure, and V3 itself is not parameterized with the current crypto slot count. The account overlay makes the final trim according to V3's rank.

One global count is simple and conservatively bounds monitoring/order-state cardinality. Separate sleeve counts would better align capacity with distinct equity/crypto mechanics, while gross/cash continue to bind shared capital; it would require a deliberate replacement for the current total-account order/position ceiling. A reservation model could make priority explicit but adds state and reconciliation obligations. These are architecture alternatives, not recommendations or performance claims. The present code explicitly favors crypto in same-cycle contention; whether that is the intended long-term governance priority is not documented by a count-risk rationale in the runtime path alone.
