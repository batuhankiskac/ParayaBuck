batch_screen_v1 | batch screening framework on research/fast_engine (deliverable: the framework;
no trading idea is evaluated by this study)

verdict
  Delivered and verified. `--harness` PASSes 59/59 checks in 36 s: it runs
  `python -m research.fast_engine.parity --quick` (PASS, 17 s) and then reproduces every anchor of
  the three example plugins through the plugin path, plus the framework's own parity cells. The
  three example arms match their published numbers to <= 0.00005 pp (the published files' own
  6-dp rounding). The `anchors_v1` batch runs stage 1 for every arm, stage 2 for the survivor,
  writes the results + scoreboard, and a second run reproduces every output file byte for byte
  (only `timing.json`, the wall-clock report, is allowed to differ).

plugin API
  idea = research/ideas/<idea_id>.py with ARMS = {arm_id: spec} and targets(data, spec), vectorised
  numpy over a (P, T) MarketData panel (days/year/month, price, legs {2x, 1x}, leg, open/close/vol,
  div, rate, high/low, meta); P = 1 on a real window, a bootstrap chunk otherwise. Spec options:
  rule (K | C0/R2 | A1u | H2 | a name registered via rules.register_rule -> fe_sim.RULE, the
  engine's own extension point), leg, cash_yield. targets may also return the held leg; a
  per-session leg switch raises NeedsKernel, as does a module declaring NEEDS_KERNEL -- such a
  trial is registered and never simulated (a new mechanism is a kernel change plus a parity cell,
  i.e. a separate study, not a batch arm).

registry / pre-registration
  research/batch_screen/REGISTRY.jsonl: one append-only line per declaration (idea, arm, spec,
  spec_hash, code_hash, batch, date, status, git). The runner REFUSES to screen an arm whose
  module's bytes differ from its bytes at HEAD (registry.require_committed) and refuses an arm
  whose declared cash_yield differs from the batch's. N (the deflation's multiple-testing count)
  counts distinct (idea, arm, spec_hash): 3 for this batch (30 lines: the framework's own
  repeated runs while it was being built -- one line per declaration, never deleted).

stage 1 (screen; main window 2000-03-09 -> 2026-09-29 + its block-20 bootstrap)
  PASS iff after-tax $100k 2000-window delta > 0 AND B1-recent (seed 20261011, block 20, 1000
  after-tax paths) median delta > 0 AND pre-tax max DD <= K + 2 pp AND turnover <= 2 x K
  (base and calibrated, m = 2).

stage 2 (holdout; stage-1 survivors only)
  G1-G9 vs K (ewma_band_v1's definitions, G9 = <= 2 x K), after tax at $100k on 2000/2010/2017,
  B1/B2 median delta >= 0 with share > 0 >= 55 %, the 21 ETFs after tax (median > 0, share >= 60 %),
  the 21 January rolling starts, the six OOS windows, the pooled OOS bootstrap (median >= 0), the
  fresh-seed bootstraps (seed 20261016, blocks 10/40, median >= 0 and share >= 55 % in all four
  cells). A failure writes its full record, so the registry counts it.

deflation (5 %)
  Over every screened arm's B1-recent delta vector (same 1000 resampled paths for every arm ->
  paired): white_rc (p = P*(max t* >= max t)), rw_stepdown (Romano-Wolf stepM, studentized max
  statistic, 2000 second-level resamples, seed 20261016, monotone p along the observed-t order) and
  deflated_sharpe (Bailey & Lopez de Prado 2014, N = distinct trials, advantage-Sharpe statistic).
  A candidate is declared iff stage 2 passes AND RW p_adjusted <= 0.05 AND DSR >= 0.95. Assumptions
  (block bootstrap as the sampling distribution, paired arms, 20-session blocks cannot capture
  longer memory) are listed in README.md section 4.

byte-identical reruns
  $ python -m research.batch_screen.run --batch anchors_v1 --ideas k_control,r2_control,vol_shape_p15
  $ cp -r research/batch_screen/results /tmp/bs_run1 ; (run again) ; cp -r ... /tmp/bs_run2
  $ diff -r --exclude=timing.json /tmp/bs_run1 /tmp/bs_run2     # -> no output
  RESULTS.json, SCOREBOARD.md, _control.json, the three per-arm files and DEFLATION.json are
  byte-identical; timing.json (per-arm wall clock + the ledger's line count) is the documented
  exception. Every float is rounded to 6 dp and every container sorted before serialising.

caveats
  * The pooled-OOS bootstrap's calendar is each market's real session list with i0 = 253,
    i1 = OOS_BOOT_L (the published `boot_oos_market` convention, reproduced bit for bit); its G8
    medians are therefore new evidence at the campaign's own seed, not a copy of vol_shape_v1's
    fixed-calendar variant. The two implementations differ in the draw (chunked vs per-path) and in
    the December calendar, so their numbers are close (both ~-0.01 pp for p15) but not identical.
  * The deflated Sharpe is computed on the bootstrap advantage distribution, not on a daily return
    series (the screening decision is made on the after-tax CAGR advantage); documented in
    README.md section 4.
  * `cash_yield = "tbill"` support is wired (stage runs and bootstraps) but off: it changes every
    published cell, so it is a batch-level flag and this batch does not use it.
  * A new execution mechanism (a second leg, a bracket budget, partial fills) is out of scope by
    construction: an idea module declares NEEDS_KERNEL and is registered but not simulated.
