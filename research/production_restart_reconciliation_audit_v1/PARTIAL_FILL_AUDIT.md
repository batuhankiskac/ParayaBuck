# Partial fills

Alpaca documents \`partially_filled\` and \`pending_cancel\` as live order states and FILL activity \`cum_qty\`/\`leaves_qty\`: [order statuses](https://docs.alpaca.markets/us/docs/orders-at-alpaca), [activity fields](https://docs.alpaca.markets/us/docs/account-activities). The repository's trade-update path persists cumulative fill and deduplicates by activity ID (\`portfolio/runtime_repository.py:844+\`); broker account positions already reflect executed quantity, and nonterminal OPEN orders remain in the broker list. The planner's slot set is a union of nonzero positions, local nonterminal order symbols, and broker OPEN symbols (\`portfolio/runtime_service.py:1490-1532\`; \`execution/portfolio.py:556-590\`), so a partial exit cannot release a slot during planning.

The startup broker/local quantity comparison may halt when a partial fill arrived while the process was down and the local fill ledger has not caught up. That is conservative exposure control but prevents automatic recovery. \`_reconcile_fill_activity_fees\` recovers some ledger BUY fills by broker ID, yet the local portfolio repository is primarily updated by trade stream/order lookup; the FILL activity function does not directly update portfolio order rows. No evidence shows a partial fill is booked twice under normal replay; existing tests exercise cumulative deduplication. The audit did not prove an exactly-once outcome for every trade-stream/REST interleaving.
