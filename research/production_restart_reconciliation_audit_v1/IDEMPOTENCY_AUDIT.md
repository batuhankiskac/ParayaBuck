# Client order ID and idempotency

Portfolio decision ID is SHA256(account ID, configuration digest, decision timestamp, market) truncated to 24 hex chars (\`portfolio/runtime_models.py:179\`). Portfolio order IDs are deterministic per decision/symbol/side (\`portfolio/runtime_service.py:1611-1621\`; planner in \`execution/portfolio.py\`). The repository persists decision and order rows before submission (\`runtime_service.py:1110-1210,1628-1641\`). Repeated local rows are skipped in submitted/terminal/ambiguous states (:1622-1631). Alpaca permits caller-supplied unique IDs and lookup by that ID: [orders](https://docs.alpaca.markets/us/docs/orders-at-alpaca), [client ID lookup](https://docs.alpaca.markets/us/v1.1/docs/working-with-orders).

If a submit times out, \`OrderService._submit_with_recovery\` looks up the same client ID (\`alpaca_orders.py:129-161\`). A non-404 lookup failure raises \`AmbiguousOrderState\`; the repository marks \`reconciliation_required\`. After a crash with a row at \`submitting\`, \`PortfolioRuntime._resolve_stuck_submission_rows\` asks the broker by client ID and updates the row (\`runtime_service.py:1311-1348\`). Full fill recovery uses broker cumulative quantity and average price (\`alpaca.py:644-708\`, \`runtime.py:1666-1694\`).

The exact C2/C3 window has a durable intent row before the broker call; a confirmed broker working order is not blindly resubmitted. A 404 after an ambiguous submit is treated as proof of absence in the recovery path, which assumes broker lookup is already consistent. That timing guarantee was not established from official documentation, so it remains a residual policy/latency risk. Portfolio idempotency proof does not automatically cover separately generated UUID stop IDs (\`alpaca_reconciliation.py:568-578\`); stop placement has its own broker lookup and protection checks.
